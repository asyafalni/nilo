# zstd is a module whose contexts are the caller's memory

**Status:** accepted
**Topic:** [zstd](../design/zstd.md)
**Applies:** [ADR 017](./017-the-trade-budget-has-four-axes.md) (the four axes, and a feature the linker cannot drop states its size), [ADR 038](./038-a-module-sits-where-the-loop-puts-it.md) (which module a file goes in), [ADR 062](./062-where-a-connection-waits-is-what-it-costs.md) (a fiber holds its stack at its high-water mark), [ADR 066](./066-a-lazy-dependency-is-a-request.md) (a flag, not a request)
**Extends:** [ADR 248](./248-gzip-is-libdeflate-when-a-build-asks-for-it.md) (a C library behind a flag, built freestanding with no libc), [ADR 211](./211-a-response-is-compressed-on-a-compressor-borrowed-from-a-pool.md) (the pool, its borrow rule and its sizes), [ADR 089](./089-a-body-under-an-encoding-other-than-gzip-is-refused.md) and [ADR 283](./283-a-route-can-read-a-content-encoding-itself.md) (a request body's coding), [ADR 273](./273-a-file-a-build-compressed-is-served-as-the-coding-of-the-file-beside-it.md) (a sibling is held to the file it sits beside), [ADR 292](./292-a-fetch-build-can-read-a-gzip-answer.md) (the second coding is a case, not a reshaping)
**Closes:** the `docs/decided.md` row *a response could be brotli or zstd beside gzip*, for zstd, and the `docs/todo.md` entry *nilo decodes no zstd request body itself*, when the second stage lands (the response side, uses 1, 4 and the answer half of 8, has landed; the request side and `nilo_fetch` are the rest)

## Context

zstd was refused for responses on one set of numbers ([`bench/result/http.md`](../../bench/result/http.md#which-deflate-is-fastest-and-whether-brotli-or-zstd-would-beat-it)): the fastest at every size, +386 KB on a program, an encoder that grows to the largest body, no encoder in the standard library, and nobody to send it to. ADR 283 then let a route read `zstd` itself, so a request was never blocked. What has changed is the caller. outpost's agent and server are both nilo programs, and every byte between them crosses a WAN uncompressed; its S2 file format stores zstd and copies a 25-file libzstd list into its own `build.zig`; and an OpenTelemetry exporter can send `zstd` to any nilo receiver (outpost's port feedback, entry 12 and the last entry). The refusal's reason was "nobody sends it", and that is no longer the case.

The case is a whole one. zstd would be used in eight places that want a context in eight different places: a compressor per thread for responses, a decoder per thread for request bodies, a streaming decoder in a request's arena for `c.bodyStream()`, a context for a static file at load, a decoder for a `nilo_fetch` answer, a compressor for a `nilo_fetch` body, a streaming compressor with a flush for a chunked upload, and the test client. Built as one place (the server) first, the next seven would each fit a shape that was made for the first. So this ADR designs all eight, builds what all eight share (the library behind a flag, the module and its contexts), and leaves the wiring of each to the second stage, which has only to call.

## Decision

### The flag and the library (built)

**`.zstd = true` on `b.dependency("nilo", …)`, `-Dzstd` in this repository, builds libzstd 1.5.7 into `nilo_zstd`. Without it nothing is fetched, built or linked** (ADR 066: `b.lazyDependency` is called only behind `want_zstd`, or `in_repo`). `nilo.app(b, .{ .zstd = true })` forwards it and imports the module into the root. `nilo_zstd` is exported whatever the flag says, so `dependency.module("nilo_zstd")` always answers; without the flag its first line is a compile error that names the line to write.

**The library is the upstream release tarball, compiled by nilo's own `build.zig`** (`zstdLibFor`, 22 files of `lib/common`, `lib/compress` and `lib/decompress`, not the dictionary builder, not `pool.c`, not `threading.c`), the way libdeflate and llhttp are (ADR 248, ADR 231), so a Zig release changes nothing and outpost's 25-file list is one `dependency.module("nilo_zstd")`. **Always `ReleaseFast` whatever the program is built as**, multithreading off (a static context cannot have workers), legacy formats off, `-DXXH_NAMESPACE=ZSTD_` so its xxhash cannot collide with a program's own, no tracing hook.

**No libc.** nilo's plain build links none, and a program using `nilo_zstd` links none either: stripped `ReleaseFast` on a `-gnu` target it is `statically linked` with no dynamic section, and Debug and ReleaseSafe link the same archive. libzstd wanted four things from a libc and each is a line: `zstd/shim/string.h` stands in for the one header it includes and declares `memcpy`, `memmove`, `memset` and `memcmp`, which compiler_rt defines; `XXH_NO_STDLIB` removes xxhash's `stdlib.h`; and `ZSTD_malloc`, `ZSTD_calloc` and `ZSTD_free` are defined away to a null (`ZSTD_DEPS_MALLOC` plus three macros), so a path that asked for memory would fail instead of calling anything. Nothing asks: `nilo_zstd` only builds `ZSTD_initStatic*` contexts, in memory the caller hands it, which libzstd's own documentation promises never calls `malloc`. `nm` over the archive shows three undefined libc symbols (`memcpy`, `memmove`, `memset`) and no weak definition of any: libzstd has no `lib/utils.c` (the trap that made ADR 248 leave one file out), because its `zstd_deps.h` is the seam libdeflate lacks.

**No assembly.** `huf_decompress_amd64.S` is `ZSTD_DISABLE_ASM`ed. With it linked and without it, decoding 1 MB of JSON took 210.2 and 212.4 µs, 1.6 MB of prose 959 and 966, 4.9 MB of machine code 3,314 and 3,372: 0.7% to 1.7%, inside what the machine moved between two runs of one binary. It would be an assembly file in the build for one architecture, for a gain nobody could see.

**One archive, not an encoder and a decoder.** The linker takes only the members a symbol asks for and `-ffunction-sections` drops the rest, so a program that only decodes does not link an encoder: stripped `ReleaseFast`, a control of 4,840 bytes, decompress only 127,816 (+122,976), compress only 414,536 (+409,696), both 521,032 (+516,192) (`zig build size-zstd`). Two libraries would have needed a flag each and bought nothing.

### The module (built)

**`nilo_zstd` is a tool module (ADR 038): it imports nothing but `zstd_build`, a generated module of one bool, and needs no event loop, so it sits in `layers` with that one entry.** `zig test zstd/zstd.zig` alone cannot work, the library being C; `zig build test-zstd` is the whole suite, in Debug and ReleaseSafe, on `test`.

**Every context is bytes the caller provides, sized by a function the module gives. The module allocates nothing for itself.**

| job | type | memory it asks for |
|---|---|---|
| a whole body into a buffer | `Compressor` | `Compressor.contextSize(options, max_src)` |
| a stream with a flush | `StreamCompressor`, a `std.Io.Writer` | `StreamCompressor.contextSize(options)` |
| a frame that announces its size, or any frame with a ceiling | `Decompressor` | `Decompressor.contextSize()` |
| a stream, or `c.bodyStream()` | `StreamDecoder`, a `std.Io.Reader` | `StreamDecoder.sizeFrom(header, options)` |
| one per executor thread | `CompressorPool`, `DecompressorPool` | one mapping, kept off huge pages |

**`Compressor`.** `compress(dst, src)` writes one frame and returns the slice, `NoRoom` when it does not fit (the caller sends the body as it is), `SourceTooLarge` over the `max_src` the context was sized for. The window is bounded by `max_src`: libzstd shrinks `windowLog` to the input, so a context for 4 KB at level 3 is 90,128 bytes and for 1 MB 1,303,568. A body smaller than `max_src` is compressed with the parameters tuned for its own size when they fit the memory (a level's table changes strategy by size, and a strategy has its own tables), and otherwise with the context's own, so a context sized by the estimate is never asked for more: held by a test across nine levels and twelve sizes, and by a test that starts the context at every 8-byte offset of a cache line. `EncodeOptions.window_log` defaults to 23, because levels 20 to 22 want windows of 32 to 128 MB and RFC 9659 caps an HTTP zstd window at 8 MB. The frame header carries the content size, so a peer can decode it in one shot.

**`StreamCompressor`.** A `std.Io.Writer` into a sink, with `flush` (`ZSTD_e_flush` and a flush of the sink) and `finish`. A flush makes every byte written so far decodable by the peer without ending the frame, which a chunked upload whose every line must arrive on time needs; it costs bytes (flushing after every 1,000-byte write is 60% larger than letting the encoder fill its blocks, still 16% of the input). The window is the caller's (`window_log`) because it is most of the memory: level 1 at 2^15 is 312,513 bytes, level 3 at 2^17 1,697,297, and a window over 2^17 bought nothing on a 164 KB stream.

**`Decompressor`.** `announced(src, window_log_max, limit)` mirrors `http/encoded.zig`'s `announcedSize`: the frame's own claim, checked before anything is allocated: the magic (`NotZstd`, not "too large", so JSON somebody forgot to compress is read as that), a window within the cap, a size no frame of this length could hold (`Corrupt`; no frame decodes to more than 32,768 times its length, a four-byte RLE block of 128 KB), and the ceiling (`BodyTooLarge`). `decode(allocator, src, limit)` allocates **exactly the announced size** when the frame says it, and decodes into it with libzstd's one-shot decoder, which needs no window (the destination is the history) and a context of 95,968 bytes whatever the frame is. **A frame that does not announce its size** (a stream's encoder cannot) gets the most `ZSTD_decompressBound` can prove from its block headers, or `limit + 1` if that is less, and the allocation is shrunk to what was used; a bomb of 16 MB of zeros in under 8 KB is `BodyTooLarge` having held at most `limit + 1` bytes (a test). A stream that lies in either direction, a truncated frame and a flipped bit are errors, never a shorter or different body.

**`StreamDecoder`.** The streaming read, for `c.bodyStream()` and for an answer read as it arrives: it counts what it decodes against `max_decoded` and stops at the ceiling rather than at the end of the frame (a test stops a 64 MB frame of zeros, a few KB on the wire, at 1 MB). Its context holds the frame's window, so it is sized from the frame's own header: `sizeFrom(header)` is 112,404 bytes for a 4 KB frame, 653,646 for 165 KB, 1,481,042 for 1 MB and 8,877,856 at the RFC cap, because libzstd keeps `min(content size, window)`. A frame asking for more than `window_log_max` (default 23, RFC 9659) is `WindowTooLarge` before its window is sized, so a peer chooses a decoder's memory only up to that number. Errors come out of the reader as `error.ReadFailed`, as std's decoders do, and `err` says which.

**Checksums.** Frames the module writes carry libzstd's content checksum by default (the low 32 bits of XXH64, four bytes, about 1% of the time), and libzstd verifies one whenever a frame has it, in both decoders. A flipped bit is `ChecksumMismatch`, where `std.compress.flate.Decompress` and `std.compress.zstd.Decompress` read the checksum and compare nothing (nilo's gzip paths check the CRC themselves). **A frame without a checksum is accepted**: browsers, curl and the CLI's defaults vary, and refusing the absence would refuse peers. `Frame.parse(bytes).checksum` says whether a frame has one, for a caller that requires it, and `Frame.matches(frame, plain)` is the `.gz` sibling check of ADR 273 without decoding: the frame announces `plain.len`, carries a checksum, and its trailer is `plain`'s XXH64. **`app.static` does not use it**: it decodes a `.zst` sibling and compares (use 4), which needs no checksum and catches a damaged block; `Frame.matches` stays for a caller that cannot afford the decode.

**Pools.** `CompressorPool(n, options, max_src)` and `DecompressorPool(n, options)` are ADR 211's shape built once for every user: all the contexts in one mapping from the page allocator with `MADV_NOHUGEPAGE` before the first write (a THP-`always` kernel makes a whole 2 MB resident on one write, ADR 248), a free flag a cache line each, and `borrow(start)` that is one `cmpxchg`, scans from `start % n` so a thread finds its own, and never waits. An empty pool answers null. The borrow must span no wait, which `compress` and `decode` satisfy because nothing parks inside them.

**Errors are a Zig error set** (`NotZstd`, `Unsupported`, `WindowTooLarge`, `Corrupt`, `Truncated`, `ChecksumMismatch`, `NoRoom`, `BodyTooLarge`, `SizeNotAnnounced`, `SourceTooLarge`, `ContextTooSmall`, `Failed`) with libzstd's own words available through `describe(detail)` for a log line.

### The eight uses (1, 4 and half of 8 built; the others designed)

The names of options below are the design's: the second stage may spell one differently, and may not change what it does. Each says what it holds, where, and what it adds to the four axes. Sizes are measured ([`bench/result/zstd.md`](../../bench/result/zstd.md)) at level 3 unless said.

**1. A response (`app.compress`). Built.** With `.zstd = true` (`-Dzstd`) the response `Pool` (`http/compress.zig`) holds a `zstd.CompressorPool` of one per executor thread next to gzip's (`Pool.zstd_slots`, a field that is `void` in a build without the flag; a gzip-only client still needs the gzip slot, and one pool of slots holding both would have made a build with libdeflate pay zstd's 1.3 MB for a slot gzip fills with 229 KB). **The choice is the highest `q` the client gives, and on a tie zstd beats gzip** (`compress.negotiateResponse`: `gzip, deflate, br, zstd` from every current browser weighs all at 1); `zstd;q=0` is a no, `*` is a yes unless zstd is named, the rule the static handler already reads. **The reason for the tie is time, and bytes only above 164 KB**, which an earlier draft of this ADR got wrong: measured through the same `Pool` (`bench/result/zstd.md`), zstd at `.default` is 1.8 times faster than libdeflate at 4 KB (5.3 against 9.6 µs), 3.6 at 41 KB and 4.8 at 1 MB, but its frame is 2.5% larger at 4 KB, 8% larger at 41 KB and 19% larger at 164 KB (libdeflate's level 6 finds more at small sizes), and 13% smaller at 1 MB and 32% at 4 MB. Against `std.flate` it is smaller or equal at every size and 5 to 25 times faster. The tie goes to zstd because the CPU is the axis a request pays (ADR 017) and the bytes are a wash where most answers are; a deployment that wants gzip passes `.zstd = false`. **A zstd that cannot answer falls to gzip when the client takes it** (every compressor out, the frame no smaller, a body over its ceiling), so choosing the better coding never makes an answer worse than gzip alone would have given, and a client that takes only zstd gets the body as it is. **`Vary: Accept-Encoding` is already on every answer that could have been compressed (ADR 211), so nothing is added**, and `Content-Encoding: zstd`, the weak ETag and the left-alone cases (206, `no-transform`, a handler's own `Content-Encoding`) are ADR 211's unchanged. `Level` maps `.fastest` to 1, `.default` to 3 and `.best` to 6: 6 takes 2.38 ms for a megabyte, about what libdeflate's default takes (2.34), so the time `max_bytes` bounds holds for every level. **`Options.zstd` (default true) is read only by a build with the flag**, and `false` there builds no zstd pool at all. The context is sized for `max_bytes` (1 MiB), **and `max_bytes = 0` means a megabyte for zstd**, because a context has to be sized for a length: a body over it goes to gzip, which has no such bound. That is 1,303,568 bytes mapped a thread at level 3, **of which 90,112 are resident after a 4 KB body and 892,928 after a megabyte**, against libdeflate's 229,376 and 376,832 (ADR 248); on 16 threads answering an 8 KB body the server's pool mapping was 2,293,760 bytes resident (libdeflate's 3,670,016, `bench/compress_rss.py`). The destination buffer is ADR 211's half the body plus 64; a body that compresses worse than half is sent as it is (`NoRoom`). One arena allocation, the compressed body, as gzip's (`test "a zstd answer costs one allocation too"`). The call writes 1,696 to 2,072 bytes of stack in ReleaseFast through `Pool.encodeAt` (libdeflate's 2,224 to 2,560, `std.flate`'s 7,528 to 7,816).

**2. A request body (`c.body()`, `c.json`, a typed body, a form, a gRPC message) (built).** `Content-Encoding: zstd` is decoded once into the arena, in place of the bytes that arrived, as gzip is (ADR 089), on a `DecompressorPool` slot: 95,968 bytes a thread, no window, and one arena allocation of exactly the announced size, checked against `max_body` first. `BodyTooLarge` is the 413, and `NotZstd`, `Corrupt`, `Truncated`, `ChecksumMismatch`, `WindowTooLarge` and a size over the ratio bound are the 400 "could not be read" gzip's bad frames already are. A frame that does not announce its size takes the `limit + 1` path above. **The build decides what the parser calls the coding**: `http1.Encoding` has `.zstd`, produced only where `nilo_build.zstd` is true (`-Dzstd`, which also imports `nilo_zstd` into `nilo_http`); elsewhere `zstd` is `.other`, a 415 naming `gzip` only, and no zstd code is linked. A route that names `"zstd"` in `bodyEncodings` gets the bytes as they arrived in either build (ADR 283), and the 415's `Accept-Encoding` lists `zstd` where the build reads it or the chain names it, once. An empty pool (an App driven with no server) takes one context from the arena, 95,968 bytes, which a request cannot do without. **The pool is the App's** (`App.decoders`, sized in `wiring.sizeDecoders` to the same thread count as the compressors, one mapping, absent from a build without the flag), reached from a `Ctx` through one pointer field that is `void` in a build without the flag (`Ctx` is the size it was) and from an HTTP/2 connection through `Host.decoders`. **A body of no bytes under the header is an empty body**, as `bodyStream` already reads one, where gzip's `inflate` of nothing is a 400.

**gRPC (decided here, built).** `grpc-encoding: zstd` is accepted under the same flag: the gRPC compression document registers `zstd` as a name beside `gzip`, `grpc-accept-encoding` lists it where it is read, and a message is decoded under ADR 220's budget exactly as gzip is: **charged by the size the frame announces, and a frame that announces none (grpc-go's and tonic's streaming encoders write none) is charged the route's whole limit**, because that is the most it may hold and the budget is the connection's memory. A message over the limit is `RESOURCE_EXHAUSTED` (8), one that does not decode is `INTERNAL` (13), as gzip's; in a build without the flag `zstd` is `UNIMPLEMENTED` (12), as every coding but gzip was.

**3. `c.bodyStream()` (built).** A `StreamDecoder` in the request arena, **made on the first read** of a zstd body and never otherwise (its size is the frame's, and the header may not have arrived when `bodyStream()` is called), as gzip's 73,000 bytes are (ADR 089). **Its size is the frame's**: 112 KB for a small announced frame, up to 8.9 MB for a frame that announces nothing and asks for the RFC's 8 MB window, which is the one place a peer chooses a number of bytes, so **`body.Options.zstd_window_log_max` (default 23, set through `bodyStreamWith`) lets a route lower it**; a frame asking for more is the 400. `max_decoded` is the route's `max_bytes`, so the ceiling counts decoded bytes, and **a frame that announces more than `max_bytes` is a 413 before its context is taken from the arena**. The layer (`body.Zstd`) is about 5 KB; a body that is cut, slow or chunked wrongly keeps the errors it had; `discardRest` decodes into a 1 KB scratch in the layer. The context is a request's arena and not a connection's: nothing is held while a connection idles.

**4. A static file. Built.** `X.zst` beside `X` is a form of `X` as `.gz` and `.br` are (ADR 273), in a build with `-Dzstd`; in any other a `.zst` is an ordinary file, as it always was. It is read by a client whose `Accept-Encoding` names it, and **verified by decoding it at load and comparing the result with `X`**, which is stronger than the trailer check an earlier draft of this ADR copied from the `.gz`: libzstd checks the frame's own checksum when it has one, the comparison covers the bytes whether it has one or not, and a damaged block under an intact trailer, which a `.gz` check accepts, is caught. So **a frame without a content checksum is used**: the zstd CLI writes one by default but libzstd's API and several build tools do not, and refusing the absence would have refused most plugins' output when the decode answers the question the checksum was asked to. The decode costs about 0.2 ms a megabyte and a 95,968-byte context freed on return, at load only. A frame that does not decode, asks for a window over the RFC's 8 MB (a browser would refuse it too), is not smaller than the file or decodes to anything else is passed over with the load line's one warning ("it does not decode to the file beside it"), and its own URL is a 404. A spilled file is never read at load, so its `.zst` is held to the modification time as a `.br` is (older than the file is passed over) and opened per request, with the ETag suffix `-zst`. An embedded tree borrows the build's frame after the same decode. **On a tie `br` beats `zstd` beats `gzip`** (`compress.negotiate` takes `have_br`, `have_zstd`, `have_gzip`): a build's brotli is the smallest, zstd decodes fastest, and a browser sends all three at 1. A `Range` still gets the plain file. And nilo makes its own copy at load as it does the gzip one: **level 12** (`zstd_load_level`, 4.8 ms for 1 MB of JSON and 40% fewer bytes than level 3; level 19 is 46 times the time for 18% fewer), in a context allocated for the load and freed after, **with its window held to 2^20** (`zstd_load_window_log`): 1,319,952 bytes for a file up to 64 KB and 13,100,048 from 1 MB up, a transient the process peaks at during the load and at every reload a `follow` makes, and gives back before the next file. A file up to a megabyte gets the window it would have had anyway. The window the file would otherwise have had was the first form, and it took **50,848,784 bytes for an 8 MB file, the default ceiling of a held file**; the cap costs 19% more bytes on a 4 MB JSON body, held for the life of the App, and was taken because a peak four times larger at every start and reload is what a small machine serving large files cannot plan around, where held bytes are on the load line (`bench/result/zstd.md`). A `.zst` sibling replaces nilo's copy, and `compress = false` turns off the copy and not the siblings, as before. **`Options.compress_zstd` (default true, and read only by a build with the flag) keeps the tree as it was**: a second compressed copy of each file is held for the life of the App and counted against `max_total_bytes`, the load line says "N of them zstd copies", and `app.openapi`'s generated document (`fromMemory`) gets one too. The held bytes of the six-file, 1.4 MB front end of ADR 273 grow by the zstd copy of each file, which is the cost of a client that wants zstd getting it from a tree that has no siblings.

**5. `nilo_fetch` reads a zstd answer.** `-Dfetch_zstd` (`.fetch_zstd = true`), the way `-Dfetch_gzip` is (ADR 292) and **independent of it**: `fetch.reads_zstd` is the second comptime constant of the generated `fetch_config`, so a program that dials out without the flag links no libzstd and its calls advertise what they did. **The flag implies `.zstd = true`** (the decoder is libzstd's, and a flag that needed another would be a second thing to forget; the reverse does not hold, and `.zstd` alone changes nothing about a call). A call sends `Accept-Encoding: zstd, gzip, identity` with both flags, `zstd, identity` with this one alone and `gzip, identity` with the other (`fetch.accepted_encodings`), and an answer under `zstd` is decoded whatever was advertised, by a `StreamDecoder`. **The decoder is two allocations from the client's allocator, the second made at the first read.** The header with a 16 KB input buffer is made when the answer announces zstd; the context is made when the first bytes of the body are in, because `StreamDecoder.sizeFrom` needs them: **112,416 bytes for a small frame that announces its length, 358,176 for 64 KB, 1,537,824 for a megabyte, 2,586,400 for a stream that announces nothing at level 3's 2^21 window, and 8,877,856 at the 8 MB window** the RFC requires a decoder to give and no frame is allowed to exceed (`WindowTooLarge` is a `BodyEncodingInvalid`). Sizing at the first read puts the wait for those bytes inside the clocks a body read is under, which `begin` is not. `max_body` is counted by the caller's reader (`take` reads under `Limit.limited(max)`), so a small answer cannot inflate past it, and `max_decoded` of the decoder is left open. A body of no bytes is an empty answer; a frame that is not zstd, does not decode, fails its checksum or ends early is `BodyEncodingInvalid`. **A second coding was a case, as ADR 292 said**: `fetch/decode.zig` gained `Coding.zstd`, the `Reading` header both decoders start with (the gzip one is `gzip.Gunzip` now) and `advertised`, and `Begin.gzip` became `Begin.decode` because the name stopped being true. `fetch`'s row in `layers` gains `nilo_zstd` (a Fitting may name a tool module); the import is lazy, so a build that reads and sends no zstd analyses none of it, and the program of `bench/release/fetch.zig` is the same 953,760 bytes at the commit before this and with it, with and without `-Dzstd`.

**6. `nilo_fetch` sends a compressed body.** `Call.encoding = fetch.zstd` for `Body.slice`, **the second `Coding` of ADR 293** and not a field of its own: the body is compressed into the call's arena, a buffer one byte shorter than the body (`NoRoom` is a body that does not shrink, which goes out as it is with no header, and the arena gives back what the frame did not use), and `Content-Length` is the compressed size. `Level` is `.fastest`, `.default`, `.best` or `.exact = n`, in words every coding has: **1, 3 and 6** for zstd (6 is ADR 211's `.best` and the last level whose compressor fits what a client keeps: 3.7 MB for a megabyte), and `exact` is libzstd's own number. **The context is not a pool.** The design above had a `CompressorPool` on the `Client` made by `Client.init` from `Settings.compress_slots`; a client has no thread index to borrow by, a pool of the machine's CPU count mapped at start-up is memory a client that never compresses should not hold, and ADR 293 had already put a compressor in a stash of one on the `Client`, so zstd's is a second `Spare` in it: heap memory sized by `Compressor.contextSize(options, body.len)` (73,744 bytes for 4 KB at level 1, 90,128 at level 3, 1.3 MB for a megabyte at 3), grown to a power of two when a later body needs more, and **freed with the call when it holds more than 4 MiB** (`stash_keep_max`), so one body at level 12 (13 MB) does not make a client carry it. **A server that does not read the coding answers 415, and the client resends once, plain, as for gzip; the answer is not remembered.** The table of 16 origins that was designed is not built: it is memory and a lock on the `Client`, a stale entry after a server upgrade, and a rule about somebody else's service; `sent_encoding == null` tells the caller who knows the server to stop asking. **A zstd body refused by a server that reads gzip goes out plain, not gzipped**: the second try as gzip would link flate into every program that sends zstd to save one body's bytes on a path the caller can choose for itself. Naming `fetch.zstd` is what links the compressor, so a program that never writes it links none; it needs `.zstd = true` and no fetch flag (that one is for reading).

**7. A streaming upload.** `Exchange.beginUpload(…, fetch.zstd)` (ADR 293) runs a `StreamCompressor` over the chunked body's writer, with `ZSTD_e_flush` on the caller's `flush`, so each NDJSON line reaches the peer whole and on time (the test decodes what has arrived up to a flush, then to the end). It holds a context for the life of the upload, in the same stash slot: **the window is held to 2^18 (256 KB), which makes the context 1,107,473 bytes at level 1, 1,828,369 at the default level 3 and 4,187,665 at `.best`**, and the frame does not announce its length, so a receiver decodes it as a stream. Above level 6 a stream's tables are far larger than its window (26 MB at level 10, 51 MB at 12, 86 MB at 19), and are freed with the upload. The 2^15 window at level 1 (312,513 bytes) the stage-1 table recommended for an upload is not what a call can ask for yet; `Coding` has `level` and no window, and a caller with a log or a process table who wants it is a field. The cost of a flush is bytes (60% on 1,000-byte pieces), paid by the caller who flushes. The same type serves a streaming response when ADR 211's "a stream is never compressed" is revisited; that is not decided here.

**8. The test client and `fetch.testing.Canned`.** *(The request half is built: `nilo.testing.zstd(arena, bytes)` writes a frame with its size and checksum, in a context from the arena; it is a compile error naming the flag in a build that does not read zstd, held by `refusals/testing_zstd_without_the_flag.zig`.)* `testing.Client` accepts a compressed answer (**built**: `answer.decoded(arena)` and `answer.json` decode `Content-Encoding: zstd` in a build that links zstd, with the decoder's 95,968 bytes taken from the caller's arena, and `bytes` and `text` stay the wire's bytes) and sends `.encoding = .zstd` on a request body, both with contexts from the test's allocator, since a test may allocate. `Canned.replyZstd(out, status, headers, plain)` is `replyGzip`'s counterpart, writing the frame into the caller's buffer so a test can damage it, and `Canned.requestBodyDecoded` undoes `zstd` as it does `gzip` (`fetch.testing.inflateZstd` is the decode it uses, for a frame a test holds); both are built. Both exist so a route and an agent loop can be tested compressed in the default `zig build test`.

### What it costs (the four axes)

| Axis | Cost |
|---|---|
| Allocations per request | none from the module itself. For `nilo_fetch`: none on a call that names no coding and reads no zstd; a zstd answer is two heap allocations (16.5 KB and the context) freed by `end`, and a zstd body is the arena allocations of gzip's (the headers and the output) with the compressor kept on the `Client` after the first. A compressed response is one arena allocation, the compressed body, as gzip's; a request body under zstd is one arena allocation of exactly its announced size; the contexts are pool slots, a `bodyStream`'s decoder is one more arena allocation made only when it is asked for. The allocation budget test must hold under `.zstd = true` before the second stage merges |
| Memory per idle connection | 0. For `nilo_fetch`, the frame of the release program's `main` (where the call chain inlines) is 5,960 bytes at the commit before and in all four builds (no flag, `-Dfetch_gzip`, `-Dfetch_zstd`, both): the decoder is a pointer on the `Exchange`, as gzip's is, and every context is on the heap. Every context is a pool slot or an arena allocation of one request, and nothing holds one while a connection idles. The stack: **a call writes 1,728 to 2,104 bytes compressing, 1,112 to 1,232 decoding one-shot, 1,608 to 1,728 decoding as a stream and 2,816 writing a stream with a flush, in ReleaseFast; up to 3,456 in Debug**, every row under one page (`zig build bench-zstd-stack`), against `std.flate`'s 7,432 to 7,968 and libdeflate's 2,272 to 2,624 |
| Throughput and p99 | zstd 3 on a 4 KB JSON answer is 4.9 µs and 745 bytes, libdeflate's default 9.1 µs and 721, `std.flate`'s 23.7 and 743; on a megabyte 488 µs and 65,985 bytes, libdeflate's 2,344 and 75,665, `std.flate`'s 6,499 and 99,794. Decoding 4 KB is 2.3 µs against inflate's 5.3, and a megabyte 212 against 516. On a body that is not JSON the byte gap closes (machine code: zstd 3 3% larger than libdeflate's default at a sixth of the time). The gain on a small answer is a few microseconds, not a factor; on a large body it is a factor of five |
| Binary size | **The default build: +0**, because a build without the flag fetches and links nothing and the files under `http/` and `fetch/` name the module only behind a build constant (`zig build test` without `-Dzstd` links no libzstd into the App). With the flag, a program pays only for what it calls: decode only +122,976 bytes, encode only +409,696, both +516,192, stripped `ReleaseFast`; the response side calls the encoder, and `app.static` calls both (the load copy and the sibling's verification). **`nilo_fetch`, measured: the program of `bench/release/fetch.zig` is 953,760 bytes stripped at the commit before and with this stage, with no flag and with `-Dzstd`; `-Dfetch_zstd` makes it 1,045,888 (+92,128, a decoder), with `-Dfetch_gzip` as well 1,068,992; a program that posts and names `fetch.zstd` is +455,904 over the same program naming no coding (`fetch.gzip` is +61,696), the cost of the encoder, which a vtable of four functions links whole.** The `hello` and `rest` rows for ADR 017's running total are not yet measured with the flag |

A pool for gzip and one for zstd both exist in a `.zstd` build, so a server that serves both holds both: at 16 threads with 1 MiB bodies, libdeflate's 10.7 MB mapped and zstd's 20.9 MB; what is resident is what the bodies touched (zstd 1.4 MB after 4 KB bodies, 14.3 MB after megabytes).

## What was rejected

**Vendoring libzstd into the repository.** 1.7 MB of C that nilo would have to keep in step and a licence file to carry; the tarball by hash, fetched only behind the flag, is what libdeflate and llhttp are (ADR 248, ADR 231).

**A pure-Zig encoder, or building on `std.compress.zstd`.** The standard library has a decoder and no encoder, and writing one is a project with no end that would be slower and weaker than a library that has had a decade of tuning. The decoder was measured and is not the better of the two on any axis: on the same frame it is 8.3 times slower than libzstd on 1 MB of JSON, 11.8 on prose and 37 on machine code (126 ms against 3.4), 13 times on a 4 KB body, and it needs a buffer of `window_len + 128 KB` (8,519,680 bytes at the RFC cap) to stream into anything, or the whole output as one fixed writer, which `c.bodyStream()` cannot give. libzstd's one-shot decoder needs 95,968 bytes and no window; its streaming decoder is sized from the frame header.

**Linking libc, or `ZSTD_createCCtx` with an allocator.** libc would put nilo's plain build's "links no libc" at the price of a flag for every dependent. `create` would hide a megabyte inside a call, take the pool's shape away (a request cannot say where its context lives) and put a `malloc` behind the allocation axis. Static contexts cost a size function and an alignment, and make the module's memory the caller's.

**The amd64 assembly**, measured above. **Two archives for the encoder and the decoder**, which the linker does by itself. **Dropping the three binary-tree strategies** to take 57,344 bytes off the encoder (414,536 to 357,192): levels above 12 would silently become 12, which is a default nobody asked for; `ZSTD_EXCLUDE_*_BLOCK_COMPRESSOR` is the knob if a program wants it.

**Requiring a checksum on a frame read.** Peers differ. The first draft of use 4 had the static `.zst` check require one (`Frame.matches`, the `.gz` trailer's counterpart) and ignore a frame without it; that would have refused the output of most build tools, and decoding the sibling at load answers the question the checksum was meant to answer, for 0.2 ms a megabyte, so a frame without one is used. **Dictionaries.** A static context cannot load one (`ZSTD_CCtx_loadDictionary` allocates, and libzstd lists it as a limitation of static contexts); `ZSTD_initStaticCDict` and `ZSTD_initStaticDDict` are the seam, and a trained dictionary for small JSON is the one thing here that would beat a factor of two on a 4 KB body. Not now, and it changes no API in this module: it adds an option.

**One flag for the server and the client.** `.zstd` links the library and turns on the server's uses; `.fetch_zstd` is `.fetch_gzip`'s counterpart, because a program that dials out is not the program that serves, and ADR 292's reason (a codec linked into every binary that dials out) applies to each coding separately.

**Compressing per request in the request arena.** A context is 90 KB to 1.3 MB, against an arena that keeps 16 KB: it would be an allocation per compressed answer and a mapping per request. The pool is the shape ADR 211 found.

**Brotli.** Unchanged: it cannot be reset or pooled, and a `.br` file the build already wrote is served (ADR 273). The `decided.md` row is split, and the part about zstd is closed by this ADR.

## How the second stage is tested

`zig build test` runs the suite as a dependent gets it, with zstd an encoding the server does not read, and `http/zstd_request.zig` in it holds that half (the 415, a route that names `"zstd"`, a gRPC message `UNIMPLEMENTED`). **The path that reads it runs under a second root, `http/test_root_zstd.zig` (`zig build test-http-zstd`), which compiles that one file with `nilo_build.zstd` on and links libzstd whatever the flag says**, the way the http root links TLS and libdeflate. Not the whole suite a second time: the root imports only that file and what it reaches. `zig build test -Dzstd` runs the whole suite with the flag and skips the second root, and a few existing tests whose expected `Accept-Encoding` or `grpc-accept-encoding` changes with the flag read `zstdbody.enabled`. A feature only tested when somebody remembers a flag is a feature that is not tested (ADR 032).
